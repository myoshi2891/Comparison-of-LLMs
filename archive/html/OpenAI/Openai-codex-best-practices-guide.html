1-3. 設定の優先順位と全体構造

CLI・IDE・アプリは同じ設定レイヤーを共有します。つまり一度整えた config.toml と AGENTS.md は全サーフェスで効きます。

2. モデルの選び方と推論レベル

2-1. 現行ラインナップ(2026-11-07 時点)

OpenAI のモデル階級は Luna < Terra < Sol < Astra(大きいほど高性能・高価格)です。この序列は OpenAI の Ted Sanders 氏が説明しています。

モデル API モデル名 API 標準価格(100万トークン) 位置づけ
GPT-6 Astra gpt-6-astra 入力 $10 / 出力 $50 最上位。長期・ツール多用・コンピュータ操作
GPT-6.1 Sol gpt-6.1-sol 入力 $2 / キャッシュ $0.10 / 出力 $10 Astra に迫る性能を 1/5 の価格で。Codex CLI の同梱カタログで既定
GPT-6.1 Terra gpt-6.1-terra 入力 $1 / キャッシュ $0.05 / 出力 $5 画面理解・コンピュータ操作・自然な文章が得意な中位
GPT-6 Luna gpt-6-luna Terra の約 1/10(Simon Willison の記述) 高速・低価格・大量処理

補足:

  • Sol / Terra / Luna / Astra は、ChatGPT の通常チャットではなく Work と Codex 向けに提供されるモデルがあります(Sol 6.1 と Terra 6.1 は発表時点で通常 Chat 非対応)。
  • API のコンテキストは 1.05M トークン(272K 超の入力は割増)ですが、ChatGPT Work / Codex 上の GPT-6.1 Sol の既定コンテキストは 500K トークンです。
  • Terra はデスクトップアプリ・CLI・API で選べますが、IDE 拡張では当面対象外と報じられています(二次)。

根拠: 公式GPT-6.1 Sol、公式ヘルプ: ChatGPT Work and Codex、開発者Simon Willison: GPT-6.1 Terra、二次Enjoy Agentic Industries: Terra、二次everruns モデルプロファイル

2-2. 選び方のフロー

筆者見解日常の既定は Sol 6.1 + medium から始め、「失敗が目立つタスクだけ上げる」運用が費用対効果の面で無難です。OpenAI の Ted Sanders 氏は、Terra について「技術的な文章は Astra/Sol より上手い場合があり、視覚・コンピュータ操作は同等で速いが、その他は少し劣る」と述べています(Hacker News コメント、Simon Willison が引用)。

2-3. 推論レベルと速度

設定 内容 使いどころ
low 速い。範囲が明確なタスク 小修正、リネーム
medium バランス型 日常の実装
high 複雑な変更・デバッグ 原因不明のバグ
xhigh / max 長時間・推論重視 大規模リファクタ
ultra 単一エージェントを超え、サブエージェントに分割 分割しやすい大タスク
Fast モード 含まれる使用量を 2.5 倍のレートで消費して高速化 急ぎのとき
Ultrafast 最大 8 倍速のトークン生成。発売時は Pro $500 など一部プラン限定 レイテンシ最優先

CLI での指定例です。

# 1回限りの非対話実行

Step 1: 環境構築と設定レイヤー

1-1. なぜ最初にやるか

公式は「品質問題の多くは実はセットアップ問題」と指摘しています(作業ディレクトリの誤り、書き込み権限の不足、モデル既定値、ツールやコネクタの欠落など)。プロンプトを工夫する前に環境を整えます。

1-2. 手順

  1. サインイン方式を決める: ChatGPT アカウントでサインインするとプランの使用量・課金が適用され、API キーを使うと API 料金になります。
  2. 個人既定値を ~/.codex/config.toml に書く(モデル、推論レベル、承認・サンドボックス方針)。
  3. リポジトリ固有の挙動を .codex/config.toml に書く(MCP、サブエージェント数など)。
  4. 一時的な変更だけを CLI 引数で上書きする。
  5. /init で AGENTS.md の雛形を作り、必ず自分のチームの実態に合わせて編集する。
  6. 診断: ネットワークまわりの不調は codex doctor --network-only(0.166.0 で追加)で切り分ける。 
# 雛形生成(CLI 内)
# /init

# 設定状態の確認(CLI 内)
# /status

# ネットワーク・接続・WebSocket の診断
codex doctor --network-only

Step 2: 権限とサンドボックスの設計

2-1. 2つのつまみ

Codex には OS レベルのサンドボックスがあり、次の2つを独立に調整します。

つまみ 決めること
承認ポリシー(approval) いつ人間に許可を求めるか
サンドボックス(sandbox) どのディレクトリを読み書きでき、何にアクセスできるか

公式の推奨は「最初は既定のまま厳しく。信頼できるリポジトリや特定のワークフローで必要が明確になってから緩める」です。

2-2. 実務上の作法

  • フル権限を最初から与えない(公式が挙げる典型的な失敗)。
  • 権限はセッション中に /permissions で変更できます。0.164.0 以降は /model と /permissions にインライン引数で渡せます。
  • ネットワーク: プロキシ層で「ホスト名の許可が先、DNS 解決は後」「Host ヘッダ重複の拒否」など防御が強化されています(0.163.0)。管理環境では許可ドメインを明示します。
  • 資格情報のマスク: リモートの Bash 実行などで資格情報をマスクする機能が入っています(0.164.0)。.env を丸ごと見せない設計を維持します。
  • 承認レビュー(Guardian): 変更履歴には、昇格した操作を実行前に審査する仕組み(Guardian)に関する項目が多数あります。OpenAI は自動レビュー側へ利用者を誘導していると報じられています二次。有効化・既定値はバージョンで変わるため、/status と公式リリースノートで確認してください。
  • 再開時の権限: スレッドの再開・フォークでは、承認済みの権限が保持されます(0.163.0 / 0.166.0)。ただし期限切れの承認を前提にしない運用が安全です。

2-3. サブエージェントと権限

サブエージェントは親セッションのサンドボックスと承認設定を継承し、カスタムエージェントのファイルでは置き換えられません。「ファイルを編集しないで」と指示しても、それはお願いであって鍵ではありません。読み取り専用にしたい場合は、そのエージェントに明示的に sandbox_mode = "read-only" を設定します。

根拠: 公式Best practices、公式Subagents、二次Releasebot: Codex 変更履歴、二次flaviocopes: subagents

Step 3: プロンプト設計とプランニング

3-1. 4要素フレームワーク(公式の既定)

公式は、プロンプトに次の4つを含めることを基本形にしています。

要素 内容 例
Goal 何を変更・構築するか 「注文 API に冪等性キーを導入する」
Context 関係するファイル・ドキュメント・エラー(@ でファイル指定) @src/orders/ と失敗ログ
Constraints 守る規約・アーキテクチャ・安全要件 「公開 API のシグネチャは変えない」
Done when 完了条件 「該当テストが通り、型チェックが通る」 
目的: 注文作成 API に冪等性キーを導入し、二重送信で注文が重複しないようにする。
コンテキスト: @src/orders/create.ts と @src/orders/create.test.ts、本番で起きた重複注文のログ。
制約: 公開 API のレスポンス形式は変えない。DB マイグレーションは追加してよいが既存列は変更しない。
完了条件: 新規テストを含む orders 配下のテストがすべて通り、lint と型チェックが通る。差分の要約と残リスクを最後に報告する。

3-2. 計画を先に立てるべき場面

  • Plan モード: /plan または Shift+Tab で切替。コンテキスト収集と確認質問を経て、実装前に強い計画を作ります(公式が最も勧める方法)。
  • インタビュー: 「前提を疑い、曖昧な点を質問してから計画を書いて」と頼みます。
  • PLANS.md(実行計画テンプレート): 長期・多段の作業向け。実行計画ガイドを参照。

開発者一方で、Peter Steinberger 氏(Shipping at Inference-Speed、2025-12-28 公開)は Plan モードを使わず、モデルと会話しながら探索して方向を決める流儀を取っています。これは GPT-5.x 世代での経験談であり、どちらが正しいかはタスクとモデル次第です。迷ったら「不可逆な変更・影響範囲が広い変更では計画を先に」と覚えると安全です。

3-3. 推論レベルの当て方

公式の目安は、速く範囲が明確なら Low、複雑な変更やデバッグは Medium〜High、長く推論の重い作業は Extra High です。最初から最大にしないことが、使用量の節約と待ち時間の短縮につながります。

3-4. 音声入力

アプリの音声ディクテーションで依頼を話すと、文脈を長く詰め込みやすくなります(公式のヒント)。

根拠: 公式Best practices、公式Prompting、開発者Steinberger: Shipping at Inference-Speed

Step 4: AGENTS.md を「痩せたまま」育てる

4-1. 公式の基本方針

AGENTS.md は「エージェント向けの README」で、自動的にコンテキストへ読み込まれます。公式が挙げる中身は次のとおりです。

項目 例
リポジトリ構成と重要ディレクトリ src/ は API、infra/ は IaC
実行方法 起動手順、必要な環境変数の名前
ビルド・テスト・lint コマンド 該当ディレクトリだけ回すコマンド
規約と PR の期待値 コミットメッセージ規約
制約と禁止事項 本番データに触れない
完了の定義と検証方法 テストと型チェックが通ること

配置は3層です。~/.codex のグローバル、リポジトリ直下、サブディレクトリ。現在地に近いファイルが優先されます。

4-2. 重要な新常識: 「長いほど良い」は誤り

ここ半年で、運用の主流が「足す」から「削る」へ変わりました。根拠は2つあります。

根拠1研究ETH Zurich らの評価(Gloaguen ら, 2026): 複数のエージェントとモデルで、コンテキストファイル(AGENTS.md など)を評価したところ、タスク成功率が改善しない(論文版の表現では低下する傾向)一方で、推論コストは 20% 以上増加しました。エージェントは指示に従うので、不要な要件は探索やテストを増やしてタスクを難しくするというのが結論です。人手で書くファイルは「最小限の要件」に絞るべきとされます。なお、ドキュメントを削除した条件では LLM 生成のコンテキストファイルが役立ったため、リポジトリから発見できない情報こそが AGENTS.md の価値です。

根拠2公式・開発者OpenAI の Eric Provencher 氏(2026-09-11, GPT-6 Astra 向け): Skills・AGENTS.md・タスクプロンプトに積み上がった古い指示は、コンテキストを圧迫して挙動を悪化させ得ると指摘しています。要点は次のとおりです。

旧来の指示 問題 改善
「編集の前に毎回、設計書 3 本を読む」 誤字修正でもコンテキストを浪費 必要なものだけ読むよう、文脈依存で文書を指す
「必ずテストを走らせて確認する」 Astra は自分でやるので過剰テストに 削除。許可したい手順だけ明記
「勝手に進めず必ず確認」など強い境界表現 続けてほしい場面でも止まる 境界の文言を見直す
最初の実装で止めて確認する要件 早めの停止に誘導される 完了条件を事前に定義(実行・確認・修正まで含める)

筆者見解Provencher 氏の記事は Astra を前提にしていますが、削る原則は Sol 6.1 など他モデルでも「過剰な手順の指示は害になり得る」という方向で有効と考えられます。ただし、モデルごとに挙動が違うため、移行時に A/B で確認してください。

4-2b. 「許可」を書くのも AGENTS.md の仕事

Astra は慎重で、安全と確信できないことはしません。安全だと分かっているワークフローには許可を与えると、無駄な停止が減ります。 

## ローカルテストについて

ローカルのテストは使い捨てのフィクスチャで動き、本番へのアクセスはありません。
実行して構いません。依頼された変更が原因の失敗は修正し、影響範囲のテストを再実行してください。
都度の承認は不要です。

4-3. 良い AGENTS.md の最小例

# AGENTS.md

## このリポジトリ
- `apps/api`: REST API(TypeScript)。`apps/web`: フロントエンド。
- 共有ライブラリは `packages/` 配下。

## コマンド(ここから発見できないものだけ)
- API のテスト: `pnpm --filter api test`
- 型チェック: `pnpm typecheck`(全体で約 90 秒かかる)

## 制約
- 本番の資格情報や `.env.production` に触れない。
- 公開 API の変更は `docs/api-changes.md` に追記する。

## 完了の定義
- 変更箇所のテストと型チェックが通っている。
- 差分の要約と残リスクを最後に報告する。

4-4. 育て方のループ

公式も「同じミスを2回したら振り返りを依頼して AGENTS.md を更新する」「ルールは繰り返しの失敗を見てから足す」「大きくなったら本体は簡潔にし、計画やレビュー用の別 Markdown を参照させる」と述べています。

棚卸しの検証質問(他社の公式ガイドにも見られる汎用的な基準): 「この行を消したらエージェントはミスをするか?」答えが「いいえ」なら消す。

Step 5: Skills とプラグイン

5-1. いつ Skill にするか

公式の目安は「同じプロンプトを繰り返し使う、または同じワークフローを直し続けるなら Skill にする」です。

手段 向いているもの
AGENTS.md 常時適用すべき、リポジトリ全体のルール
Skill 特定の作業でだけ必要な手順(ログ調査、リリースノート、移行計画など)
プラグイン Skill や連携を配布したいとき(複数 Skill、アプリ連携の同梱)
自動化 手順が安定した繰り返し作業のスケジュール実行

5-2. Skill 設計の5原則

  1. 1つの Skill は1つの仕事に絞る。
  2. description は短く、いつ使うかを明確に。名前と説明は常にコンテキストへ載るため、長すぎる・競合する・「選んで!」と主張する説明は害になります。Skill が増えすぎると、説明が短縮されて選びにくくなります。
  3. 段階的開示(progressive disclosure): ルートの SKILL.md は最小限の案内役にし、詳細は参照ファイルやスクリプトへ。
  4. 手順書ではなく判断基準を書く: 精緻な旅程のような手順は、最近のモデルでは逆効果になり得ます。
  5. 無差別にダウンロードしない: 多すぎる Skill は、各説明の見える量を減らし、選択を難しくします。 
---
name: db-migration-review
description: DB マイグレーションを追加・変更するときだけ使う。互換性とロールバックを確認する。
---

# DB マイグレーションレビュー

確認観点は `references/checklist.md` を参照。本文には詳細を書かない。

悪い description の例は「データベースに関することなら何でも使う」です。DB に触れるたびに読み込まれ、不要な指示でコンテキストを消費します。

5-3. 配置場所とスキル作成

場所 用途
$HOME/.agents/skills 個人用
.agents/skills(リポジトリ) チーム共有。新メンバーのオンボーディングにも有効
プラグイン 広く配布

雛形は $skill-creator で作ります。最初はローカルで反復し、広く共有する段階でプラグイン化します。リポジトリの Skill は他のメンバーのエージェント(別モデルかもしれない)も導くため、「どのモデルが使うか」を意識して書きます。

Step 7: 検証ループとレビュー

7-1. 「生成して終わり」にしない

公式は、Codex にテストの作成・実行・確認・レビューまで担当させることを勧めています。ただし「良い状態」が何かを知らせるのは、プロンプトか AGENTS.md の役割です。

7-2. /review の使い分け

対象 用途
ベースブランチとの比較 PR スタイルのレビュー
未コミットの変更 手元の作業の確認
特定コミット 後追い確認
カスタム指示 観点を指定(セキュリティ、性能など)

チームで code_review.md を作り、AGENTS.md から参照すると、レビューの観点がリポジトリや担当者を跨いで揃います。GitHub 連携では PR への自動レビューや @codex review が使え、OpenAI 社内では Codex が全 PR をレビューしているとのことです。 

## Review guidelines

- 認可チェックの漏れを最優先で指摘する。
- 例外の握りつぶしは P1 として扱う。
- スタイルの好みは指摘しない。

レビュー指針は、変更ファイルに最も近い AGENTS.md のものが適用されるため、重点パッケージには深い階層に個別の指針を置けます。

7-3. 実例が教える限界: 見た目のバグは見落とす

Simon Willison 氏は、Codex Desktop(GPT-5.6 Sol Ultra、サブエージェントを積極活用するモード)に、同一プロンプトでゲームを一発で作らせました。52 分で、API 料金換算では約 $23 の作業でしたが、キャラクターの目が巨大な球になっているバグを、開発中にスクリーンショットを見ていたにもかかわらず自分では発見できませんでした。人間が「なぜ巨大な黒い球があるの?」と聞き、「直して」と頼むと解決しました。

筆者見解教訓は3つです。

  1. 視覚的な品質は、自動検証の対象に含めても漏れる。人間の確認か、具体的な視覚仕様(チェックリスト)が要る。
  2. 一発で作らせた後の短い追撃プロンプトが非常に効く。
  3. 検証コストは、使用量見積もり(API 換算)に含めて考える。

根拠: 公式Best practices、公式GitHub Code Reviews、開発者Simon Willison: Moonlight & Mayhem(上記 gpt タグ一覧内の記事)

Step 8: 並列化(worktree とサブエージェント)

8-1. 3つの並列手段の違い

手段 何が並列になるか 向く場面 主な注意点
複数スレッド 独立した作業単位 別々の機能・調査 同じファイルを触らせない
Git worktree ファイルシステムの隔離 同一リポジトリで並行編集 マージ計画
サブエージェント 1タスク内の分担 探索・テスト・トリアージ トークン消費が増える

公式の失敗例として、「同じファイルに対して複数のライブスレッドを worktree なしで走らせる」ことが挙げられています。

8-2. サブエージェントの設定

組み込みの役割には default(汎用)、worker(実装・修正)、explorer(読み取り中心の探索)があります。独自のエージェントは TOML ファイルで定義します(個人は ~/.codex/agents/、プロジェクトは .codex/agents/)。必須フィールドは name、description、developer_instructions です。 

# .codex/agents/pr-explorer.toml(例)
name = "pr_explorer"
description = "PR の変更点を読み取り専用で調べ、影響範囲を要約する担当。"
developer_instructions = "コードを編集しない。根拠となるファイルと行を挙げて要約する。"
sandbox_mode = "read-only"
model_reasoning_effort = "medium"
  • 既定は agents.max_threads = 6、agents.max_depth = 1。深さを上げるとコストが乗算されるので、多くのワークフローは深さ 1 で十分です。
  • カスタムエージェントは狭く、意見を持たせる(1つの明確な仕事)のが公式の助言です。
  • 使うモデルの目安: 曖昧で多段の仕事には gpt-6.1-sol、速く狭く大量の仕事には gpt-6-luna(公式ドキュメントの提案を二次情報が要約)。
  • サブエージェントは明示的に頼んだときだけ使われ、各子が独自にモデルとツールを使うため、単一エージェントより多くのトークンを消費します。
  • 推論レベル ultra は、分割しやすい大タスクでサブエージェントへ展開します。

8-3. セッション管理のコマンド

コマンド 用途
/agent 並列エージェントのスレッド切替
/fork 元の履歴を保ったまま新スレッドへ分岐
/resume 保存済み会話の再開
/side 横道の会話。スレッド切替後に戻れる
/compact 長くなったスレッドの要約(自動でも行われる)
Command Center エージェントタスクの一覧、ピン留め、履歴のページング

1つの作業単位に1つのスレッドが原則です。同じ問題の続きなら同じスレッドで推論の軌跡を保ち、本当に枝分かれするときだけフォークします。

Step 9: 長時間タスクとコンテキスト管理

9-1. モデル側の進化

  • GPT-5.1-Codex-Max 以降、モデルが複数のコンテキストウィンドウを跨いで作業するコンパクションが前提になりました。
  • GPT-6 Astra では、履歴を繰り返し要約し直す代わりに、ノートをコンテキスト間で保持しつつ、過去のコンテキストを検索可能に保つ変更が Codex に入ったと報じられています(二次)。
  • Codex 自身も使用状況を監視し、長いタスクでは自動で要約して不要な詳細を捨てます。

9-2. /goal で「終わり」を定義する

長期タスクは /goal(目標モード)を使います。有効化は設定の features.goals = true、または codex features enable goals です。アプリでは進捗がコンポーザの上に表示され、一時停止・再開・編集・クリアができます。

良い目標は、成功を判定できる(具体的な成果物、測定可能な目標値、テスト条件)ことが重要です。 

/goal JavaScript から TypeScript へ移行する。完了条件: `pnpm typecheck` がエラー 0 件、`pnpm test` が全件成功、公開 API のエクスポート名が変わっていない。進捗は 20 ファイルごとに MIGRATION.md の表へ記録する。

二次解説では、目標のプロンプトは「タスク説明」と「終了条件」を兼ねるため、「パフォーマンス改善」のような曖昧な目標は恣意的な判定を招く、と指摘されています。

9-3. 長時間運用のライフサイクル

9-4. 実務ポイント

  • スレッドは使い捨てのチャットではなく作業場: 決定事項と文脈が蓄積するので、再説明のコストが減ります。
  • 記録をファイルへ: OpenAI の Codex 責任者 Thibault Sottiaux 氏は、自分の考えや目標をファイルに書いて Codex に参照させる習慣があると語っています(Latent Space のプロフィール)。長期運用では TODO・意思決定・ブロッカーを同期フォルダに置く方法も紹介されています。
  • 「理解」まで委譲しない: Sottiaux 氏は、実行だけでなく理解まで委ねると、利用者自身の把握が弱くなる危険を警告しています。PR の説明は必ず自分で読んでください。
  • キュー: codex queue --resume で、メッセージをキューに積んだ後にスレッドを再開できます(0.166.0)。作業中に追加の指示を送って即座に舵を切る(Steer)こともできます(0.163.0)。
  • Codex Cloud: PC がスリープしても動くので、長時間・非同期の仕事に向きます。モバイルの Remote タブで承認・進捗確認ができます。

根拠: 公式Prompting、二次FoneArena: GPT-6 Astra の機能、開発者Latent Space: Thibault Sottiaux、開発者Simon Willison: GPT-5.1-Codex-Max、二次Releasebot: Codex 変更履歴

Step 10: 自動化と CI への組み込み

10-1. 「スキルが方法、自動化がスケジュール」

手順がまだ人の細かい介入を要するなら、先に Skill 化し、予測可能になってから自動化します。公式が挙げる失敗例は「手作業で安定していない繰り返し作業を、いきなり自動化する」ことです。

自動化に向く作業 補足
直近のコミット要約 毎朝のスタンドアップ用
バグの兆候のスキャン 結果は人が確認
リリースノート下書き 週次
CI 失敗の確認 原因の一次切り分け
定期的な分析 スケジュール実行

アプリの Automations タブで、プロジェクト・プロンプト(Skill の呼び出し可)・頻度・実行環境(専用 worktree かローカルか)を選べます。振り返りにも使うと効果的です。最近のセッションを要約させ、繰り返す摩擦を AGENTS.md や Skill の改善に反映させます。

10-2. 非対話実行

# CI などでの一発実行(モデル指定)
codex exec -m gpt-6.1-sol "失敗している統合テストの根本原因を調べて修正して"

SDK(TypeScript など)からの呼び出しにも対応しています。企業環境では、Vertex AI(model_provider = "gcp")や Amazon Bedrock も使えます。 

# Vertex AI を使う例(0.165.0 で追加された組み込みプロバイダ)
model_provider = "gcp"

10-3. チーム運用の注意(開発者の指摘)

開発者AI コーディングツールを配布しても配信速度が変わらないのは、コード生成の1ノードだけが自動化され、周辺の計画・レビュー・テスト・デリバリーが従来のままだからだ、という分析があります(HackerNoon 記事、Steinberger 氏の記事を引用)。個人では推論時間が律速になりますが、チームではタスクを生み出すプロセスが律速になります。プロセス側(テスト、レビュー、ドキュメント)に投資してください。

根拠: 公式Best practices、公式Automations、二次HackerNoon、二次Releasebot: Codex 変更履歴

Step 11: コストと使用量の最適化

11-1. 使用量の仕組み(押さえるべき点)

  • ChatGPT アカウントでのサインインはプランの使用量を消費し、API キーは API 料金です。
  • Astra は GPT-5.6 Sol より使用量を速く消費する場合があります(タスク、入出力サイズ、推論レベル、速度設定で変わる)。
  • Terra は同じ使用量枠で、GPT-5.6 Terra より多くの作業ができ、Sol 6.1 や Astra よりも大幅に多くできるとされています(固定倍率は公式に明記なし)。
  • Fast モードは 2.5 倍レートで消費します。Ultrafast は最大 8 倍速で、発売時は Pro $500 や一部の企業プランに限定されていました。

11-2. コスト削減の優先順位

  • GPT-6.1 Sol のキャッシュ入力は $0.10/100万トークンで、入力の 5%、GPT-6 Sol より半額です。エージェントの長い会話ほど効くため、プレフィックス(システム指示・AGENTS.md・ツール定義)を安定させるのが有効です(Hacker News のコメントも「Codex では実利が大きい」と評価)。
  • GPT-5.6 以降は、キャッシュ書き込みが非キャッシュ入力の 1.25 倍、読み取りが 90% 割引という課金体系になっています。
  • 一次情報で確認: Plus プランのメッセージ上限などは変動するため、公式の料金ページで最新値を確認してください。

Step 12: セキュリティと Daybreak

12-1. エージェント利用の基本姿勢

  • 最小権限で始める(Step 2)。
  • 外部から取り込む内容(Web、Issue、MCP の戻り値)は信頼できない入力として扱い、プロンプトインジェクションを想定する。
  • 資格情報はマスクし、本番系へ到達できないテスト環境を使う。
  • 共有ドキュメント・サブエージェントの権限継承を理解する(Step 2-3)。

12-2. Astra の安全装置を理解する

GPT-6 Astra は OpenAI で初めて、サイバー面の Preparedness Framework で最高の Critical に分類されたモデルです。Codex では、安全装置が働くと実行前にレビューを促す表示が出ることがあり、無害な作業でも誤作動し得ると OpenAI 自身が認めています(API ではタスクが停止することもある)。0.166.0 では、安全ブロックの説明と、より安全な後続プロンプトの選択肢が TUI に追加されました。

12-3. Daybreak と Codex Security

Daybreak は OpenAI のサイバー防御プログラムです(2026年5月に開始)。Codex Security(リポジトリをスキャンし、編集可能な脅威モデルを作り、隔離環境で脆弱性を検証し、修正案を提示する)と、サイバー向けモデルなどを統合します。

階層 内容
Daybreak Blue 承認された防御者向け。汎用の最前線モデルを、セキュリティ作業向けに調整した安全装置で提供。ほとんどの防御者の出発点
Daybreak Red 高度な脆弱性調査、エクスプロイト検証、ペネトレーションテスト、レッドチーム向けの特化モデル

Codex のバージョンによって、Daybreak の既定の有効/無効や API キーでの利用条件が変わってきた履歴があります(0.161.0 では「明示的に有効化」、0.163.0 では「対象アカウントで既定有効」)。自分の環境の挙動は /status と公式リリースノートで確認してください。個人の参加者には、2026年9月1日からハードウェアセキュリティキーの採用が求められると報じられています。

13. 新モデルへの移行チェックリスト

新しい世代への移行は、棚卸しの好機です。Provencher 氏は「Codex に、記事の内容に基づく監査をさせる」ことも勧めています。

チェック項目 質問
AGENTS.md 各行を消したらミスが起きるか。リポジトリから発見できる情報を重複していないか
Skill description は「何を・いつ」だけか。他の Skill と競合しないか。ルートは案内役か
読み取り指示 「毎回全部読む」を「必要に応じて」に変えたか
テスト指示 モデルが自発的にやることを過剰に命じていないか
境界表現 強すぎる確認要求で止まっていないか。許可すべき安全な手順に許可を与えたか
完了条件 実行・確認・修正まで含めて事前に書いたか
持続性 「最初の実装で止めて確認」という要件が不要に早い停止を招いていないか
公式の移行支援 $openai-docs Skill を使った移行(GPT-5.5 時代から提供)や、CLI 同梱の OpenAI Docs 移行ガイド(GPT-6 系の推論・ツール・データ所在の観点を追加)を活用したか

開発者Simon Willison 氏は、GPT-5.5 の公式プロンプトガイドを引用し、「前の世代のプロンプトを全部引き継がず、製品要件を保てる最小のプロンプトから新しいベースラインを作る」という OpenAI の推奨が興味深いと述べています。

14. アンチパターン集

アンチパターン なぜ悪いか 代わりに
毎回の依頼に恒久ルールを書く 重複と肥大。再現性が低い AGENTS.md か Skill へ
