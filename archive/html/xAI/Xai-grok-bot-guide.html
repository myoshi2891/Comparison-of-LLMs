2Grok Bot とは何か

2.1 ひとことで言うと

Grok Bot は、あなた専用の「クラウド上のコンピュータ」を持ち、名前付きの役割(Bot)として継続的に仕事をしてくれる AI チームメイトです。ブラウザ、ターミナル、ファイル、アプリ連携(MCP を含む)を使って作業し、スケジュールやイベントで自律的に動かすこともできます。

2.2 チャット型 AI との違い

観点 一般的なチャット AI Grok Bot
動く場所 会話ウィンドウの中 永続するクラウドコンピュータ
記憶 会話ごと(機能による) Bot ごとに役割・やり方を覚えさせる
操作できるもの 主にテキスト ブラウザ・ファイル・ターミナル・連携アプリ
起動のきっかけ あなたの発言 発言 + スケジュール / イベント / X での @bot
リスク 回答の誤り中心 実際の操作(送信・変更・削除)による被害

2.3 用語集

用語 意味
Bot 役割を持った AI の個体。1 Bot = 1 つの主な仕事が基本
共有クラウドコンピュータ あなたのアカウントに 1 台割り当てられる計算環境。あなたの個人 Bot はすべてこれを共有する。Shared Bot は、メンバー自身のチャットではそのメンバーのコンピュータを、Slack チャンネルやグループチャットでは Shared Bot 側のコンピュータを使う
Skill 作業手順・判断ルール・出力形式をまとめた再利用可能な指示
Routine 「いつ(スケジュール/イベント)」「どの Bot が」「何を」実行するかの定義
Approval(承認) 重要な操作の前にあなたに確認を求める仕組み
Auto Review 実行前にモデルがツール呼び出しやPC操作を審査する機能
Take over パスワード入力などをあなた自身が行うための操作引き継ぎ
Team Bot Cursor チームのメンバーが一緒に話しかけられる共有 Bot
@bot X(旧Twitter)の投稿から自分の Grok Bot にタスクを渡す宛先

3全体像をつかむ

3.1 構成図

読み取るべきポイント

  • Bot は複数作れますが、すべて同じクラウドコンピュータを使います。
  • ブラウザとターミナルの通信は共有クラウドコンピュータから出ますが、リモート MCP 接続は Cursor バックエンドから発信され、接続アプリの OAuth トークンはコネクタのバックエンドに留まり PC には置かれません。
  • したがって「Bot を分ければ権限も分かれる」わけではありません(公式ドキュメントも「別々の Bot をセキュリティ境界として使わない」と明記しています)。詳細は 14章。

3.2 学習の道筋

4Step 0: 始める前の準備

4.1 必要なもの

公式の「Get started」によると、次が必要です。

4.2 プライバシー設定(最初に確認)

  • Grok Bot は クラウドへのデータ保存が必須で、Cursor の Legacy Privacy Mode は非対応です。
  • Legacy Privacy Mode のアカウントは、対応するデータ設定へ切り替えないと開始できません。
  • 学習利用のオプトアウトは、個人アカウントではそのアカウントのプライバシー設定に、チームのメンバーではチームの Privacy Mode(Team Settings で確認)に従います。

4.3 ベストプラクティス

  1. 本番データや機密を扱う前に、プライバシーとセキュリティの公式ページを読む。
  2. 最初の1週間は「練習用の安全なデータ」だけで試す。
  3. 会社で使うなら、社内のセキュリティ部門に先に相談する(Cursor 側にホスト、オンプレ不可という前提も確認事項)。

OS 手順の要点

アーキテクチャの確認コマンド(Linux):

  • 配布元: x.ai/bot

6Step 2: サインインする

  1. ウェルカム画面で Sign in を選ぶ(Grok Bot は Cursor アカウントを使い、専用のログインはない)。
  2. 開いたブラウザで認証を完了する。Cursor から始めた場合でも、Cursor または Grok が xAI 共通のサインインページを開くことがあり、そのページには Grok や xAI のロゴ・名称が表示される場合がある。複数のアカウントを持っている場合は、使うつもりのアカウントを選ぶ。通常は Cursor アカウントで認証する。セルフサーブの Grok Business のシートで使う場合は、ブラウザで Sign in with Grok を選び、シートを持つ Grok アカウントで認証する。
  3. アプリに戻る。
  4. 契約経路に応じて、次の手順を行う。
    • The X Subscription の Premium・Super・Ultra の場合: Grok Bot が含まれるため、Grok アカウントの連携は不要。
    • SuperGrok の場合(Cursor Enterprise のユーザーは対象外。次の Enterprise の手順に従う):
      • デスクトップ: Settings → Usage & Billing → Get Access with Grok を開き、SuperGrok の Grok アカウントでサインインする。
      • iPhone / Android: アクセス画面で Link Grok Account を選んで連携し、終わったら Finished Linking? Refresh My Status を選ぶ。
    • X Premium+ の場合:
      • デスクトップ: Settings → Usage & Billing → Get Access with Grok を開き、X Premium+ の Grok アカウントでサインインする。
      • iPhone / Android: アクセス画面で Link Grok Account を選んで連携し、終わったら Finished Linking? Refresh My Status を選ぶ。
    • Cursor Enterprise の場合: 管理者がチームに対して Grok Bot を有効化する必要がある。個人の SuperGrok アカウントは連携しない。利用可否や使用量は、管理者またはアカウント担当者に確認する。
    • セルフサーブの Grok Business で、先に Cursor アカウントで認証してしまった場合: いったんサインアウトし、Sign in with Grok でシートを持つ Grok アカウントを使って認証し直す。

初回は短いイントロのあと、裏側でコンピュータのセットアップが走り、「Grok Bot」という名前の最初の Bot が作られてチャットが開きます。

組織で SSO が必須の場合は、通常の組織サインインを完了してください。

7Step 3: 最初の Bot を設定する

7.1 原則: 1つの Bot に 1つの主な仕事

公式ガイドは「焦点を絞った Bot のほうが有用な文脈を蓄積する」と述べています。万能 Bot 1体より、役割別の Bot を勧めています。

7.2 最初のメッセージの型

最初のメッセージで「役割」「やり方」「禁止事項」「覚えること」を伝えます。

あなたの担当はプロダクトの性能分析です。
監視ツールを使って性能に関する質問を調べてください。
リンクとスクリーンショットを残し、「証拠」と「仮説」を分けて書き、
影響が最大の問題から先に報告してください。
本番設定は絶対に変更しないでください。
これを今後の作業のために覚えておいてください。

上記は公式ガイドの例を日本語に意訳したものです。

7.3 Bot を増やすタイミング

  • 仕事の種類が自然に分かれたとき(例: 分析 / 調査 / 資料)。
  • 追加はサイドバーの +(または New Bot)から。チームのユーザーはメニューから Create a Bot を選ぶ。
  • Cursor チームでチームメイトと共有したい場合は、サイドバーの + → Create a Bot で Bot を作り、チャットの Bot 名メニューにある Share からチームに共有します。

8Step 4: 良い依頼の書き方(5要素)

8.1 5要素テンプレート

# 要素 問い 例
1 Outcome(成果) 何が完了していればよいか 「先週の新規ユーザー活性化率を過去4週と比較」
2 Sources(情報源) どのアプリ/サイト/ファイルを見るか 「分析ダッシュボード」
3 Constraints(制約) やってはいけないこと、事前確認すること 「ダッシュボードは変更しない」
4 Deliverable(成果物) 何を返すか 「最大変化のステップと調査計画案」
5 Review point(確認点) どこで止まってあなたに見せるか 「計画案の時点で一度止まる」

8.2 5分でできる最初の練習(ログイン不要)

文書を1つ添付して、次のように依頼します(公式例の意訳)。

この文書を5つの箇条書きで要約してください。
日付・決定事項・未解決の質問は、別セクションにすべて列挙してください。
各項目にページまたはセクションを引用元として付けてください。
元ファイルは変更しないでください。

8.3 ツールを使う2つ目の練習

分析ダッシュボードを開き、今週の新規ユーザー活性化率を
過去4週と比較してください。
最も変化が大きいステップを特定し、
関連するグラフへのリンク付きで簡単な調査計画案を作ってください。
ダッシュボードは一切変更しないでください。
必要ならログインを私に依頼してください。

8.4 悪い依頼と良い依頼

悪い例 問題 良い例
「売上を見といて」 成果・範囲・形式が不明 「先月の売上を地域別に集計し、前年同月比を表で。数値の出典リンク付き」
「メール返しといて」 送信までやってしまう恐れ 「返信案を3パターン作成。送信しない。承認を求める」
「いい感じに整理して」 基準がない 「ファイル名を YYYY-MM-DD_内容 に統一。リネーム前に一覧で確認を」

8.5 音声入力

  • デスクトップは Cmd/Ctrl+D で音声入力、Start voice chat でライブ会話。
  • モバイルは Start dictation。

9Step 5: ログインは自分で行う(Take over)

9.1 なぜ引き継ぐのか

Bot がログインを必要とするアプリに到達すると、まず安全な方法で処理しようとします。個人 Bot は Vault、接続済みのパスワードマネージャ、または安全なシークレット入力フォーム(Secure Form) を使います。Shared Bot では、メンバー個人の Vault は使いません(公式の Vault ページは「Vault は Shared Bot では非対応」とし、キーは Shared Bot の Secrets に追加するよう案内しています)。代わりに、接続済みのパスワードマネージャまたは Secure Form で処理します。ただし v0.78.1(2026年10月27日リリース。チーム向けの変更)の changelog では、Manager が Configure → Tools から Team Bot 専用の Vault にログインを追加でき、Bot はそのログインでチームとしてサインインできるとされています。同じリリースで管理画面の名称が「Shared Bots」に変わっているため、ここでの Team Bot はチームで共有する Bot(Shared Bot)と同じ範囲とみられます。この機能は アプリ v0.78.1 以降が必要で、段階的に配信(rollout)されているため、すべてのチームですぐ使えるとは限りません。Vault のドキュメントはまだこの変更を反映していないため、利用前にアプリのバージョンと Configure 画面で確認してください。Shared Bot が応答しているメンバー本人の個人アカウントを使う場合は、使う前にそのメンバーへ確認を求めます。オーナーまたは Manager が Shared Bot に追加したアプリやシークレットを使う場合は、この確認は求められません。SSO・パスキー・CAPTCHA など、フォームでは扱えない手順がある場合にだけ、あなたにコンピュータ操作を引き継ぐ(Take over)よう依頼します。引き継いだときは、パスワード・パスキー・2要素コード・CAPTCHA・決済確認などの機密情報や確認事項を自分で入力します。

Shared Bot のセッション保存先: Slack の DM では通常そのメンバーのコンピュータ、Slack のチャンネル・スレッド・グループ DM・グループチャットでは Shared Bot のコンピュータにセッションが残ります。プライバシー設定によって別のコンピュータが選ばれる場合もあるため、常に共有PCに残るとは限りません。

9.2 守ること

やる やらない
Take over で自分が入力する チャットにパスワードやワンタイムコードを書く
Bot が出す安全なシークレット入力フォームに入力する(値はマスクされ、トランスクリプトとモデルから除外) Bot を汎用のパスワードマネージャとして使う
不要になったらサービスからサインアウト ログインしたまま放置する

9.3 ハードウェアセキュリティキー

  • YubiKey などは、Settings → General → Security Key の Use hardware security keys が有効なら、デスクトップに挿したキーを Bot のブラウザで使えます。
  • macOS / Windows ではデフォルトでオン、Linux は未対応、使用のたびに承認が必要です。

注意: ログイン済みのセッションは共有コンピュータに残り、他の Bot も使える可能性があります(14章)。

10Step 6: 結果をレビューして育てる

10.1 レビューの観点

観点 確認すること
正確性 数値・日付に出典リンクがあるか
範囲 頼んでいないことまでやっていないか
形式 指定したフォーマットか
停止位置 承認ポイントで止まったか

10.2 「恒久的な好み」は明示して覚えさせる

今後の週次レポートはこの形式にしてください:
箇条書き5つ、出典リンクは本文中にインライン、
最後に「要判断事項」というセクションを付ける。
  • 一回限りの修正と、今後も守ってほしい好みを区別して言葉にするのがコツです。
  • 手順が安定したら、Skill 化または Routine 化します(次章)。

11Step 7: Skill 化 → Routine 化

11.1 自動化の正しい順番

公式ドキュメントの原則は「まず一回限りのタスクで始め、信頼できるようにし、手順を Skill として保存し、それから自動化する」です。

11.2 良い Skill に書くこと(6項目)

# 項目
1 いつ使うか
2 必要な入力とアクセス
3 作業の順序
4 結果の検証方法
5 返すもの
6 承認が必要なこと

Skill 保存の依頼例(公式例の意訳):

いまの手順を「Weekly account health」という Skill として保存してください。
参照するシステム、リスクの定義、出力形式、
そして「顧客への連絡は必ず承認が必要」というルールを含めてください。
  • 保存済み Skill は、依頼文の中で Skill 名を指定すると呼び出せます(/ メニューは対応しているインターフェースでのみ使えます)。@ で Bot・グループ・Routine・アプリを参照できます。
  • Skill は全 Bot で共有されるライブラリですが、Bot にそのアプリやログインがないと使えない場合があります。
  • 現在の Bot で Private Skill が表示されない場合は、Connect apps を開き、接続済みの項目から Private skills を有効にします。
  • 提供されている場合、Teach a task でブラウザ操作を一度やって見せて Skill を作れます(最大10分間の画面操作を記録。マイク音声は記録しない)。作られた Skill は下書きなので、判断ルール・失敗時の扱い・承認境界を必ず追記してください。

11.3 Routine の作り方

Routine を所有させたい Bot に頼みます(公式例の意訳)。

平日の毎朝8時に、現在のアカウント一覧に対して
「Daily customer-risk」Skill を実行してください。
リンク付きのウォッチリストをこの会話に投稿してください。
顧客には連絡しないでください。
元データが取得できない場合は、古いデータを使わず失敗を報告してください。

必ず確認する6点: 所有 Bot / スケジュールとタイムゾーン / 入力元 / 期待する結果 / 承認境界 / ソース欠落時の動作

11.4 Routine の制限(公式記載)

項目 内容
1 Bot あたりの Routine 数 最大 50
実行記録 Routine ごとに直近 20 件
スケジュール間隔 最短 5 分
削除 即時・元に戻せない。Bot を削除するとその Bot の Routine も消える
長期不在 応答がなければ Routine が一時停止されることがある
1時間あたりの実行数 全 Routine 合計で 300 回、Routine ごとに 200 回まで。超過分の実行は失敗し、自動では再試行されない

11.5 イベントトリガー

Slack のメッセージや GitHub の通知をきっかけに Routine を動かせます(Cursor アカウントの連携。Slack/GitHub アプリとは別の接続が必要な場合あり)。 

#customer-escalations チャンネルに、サポートチケットへのリンクと
「needs repro」という語を含むメッセージが来たら、
チケットを開き、ステージング環境で再現し、
再現パックをこの会話に投稿してください。
承認なしに Slack へ投稿し返すことは絶対にしないでください。

「新着メッセージすべて」のような広すぎるトリガーは避ける。ノイズが増え、使用量を消費し、無関係な入力に反応するリスクが上がります。

11.6 Test の注意点

Test 実行は本物の作業を行います(Webサイトの操作、ファイル変更、連携ツールの呼び出し)。安全な入力を使い、書き込み系は承認の後ろに置いてください。

第三者のレビュー記事(eesel)も「ドライランモードはなく、テストは実行そのもの」と指摘しています。

11.7 信頼できる Routine の設計7原則

  1. 実行より準備を自動化する
  2. まず下書き・突合・推奨を作らせる
  3. 送信・購入・削除・公開・本番変更は承認必須
  4. データなし/古いデータのときの方針を書く
  5. リトライは冪等に(二重実行しても安全に)
  6. 部分完了の報告先を指定する
  7. Webサイトやデータ形式が変わったら再テスト

12Step 8: X から @bot でタスクを渡す

12.1 何ができるか

X の投稿やリプライで @bot をタグ付けすると、その投稿をあなたの Grok Bot へのタスクとして渡せます。 

@bot このスレッドを要約して、要点を私の Slack に送って
  • @bot は X 上では短い受領返信のみ。実際の作業と結果は Grok Bot アプリの Bot の会話に残ります。
  • Bot が受け取るのは、あなたの投稿・返信先の投稿・それらが引用する投稿(静止画を含む)です。
  • 初回は、タグ付き依頼が自動で作業を開始し、Grok Bot の使用量を消費する旨の通知が X から届きます。

12.2 前提条件

条件 内容
Grok アカウントと X の連携 grok.com の Settings → Account で 𝕏 Account を Connect
Grok Bot の利用権 同じ Grok アカウントで有効
自分の Bot 少なくとも1体(共有された Bot ではタグ依頼を受けられない)
地域 X に登録された国が対象地域であること

12.3 利用できない地域(公式記載)

  • オーストラリア、英国、EU、アイスランド、リヒテンシュタイン、ノルウェーの X アカウントでは現時点で未対応。
  • 判定は X に登録されている国で行われ、現在地や VPN は無関係です。
  • 国が広域(例: South Asia)や未設定の場合も未対応です。

12.4 セキュリティ上の注意

X の投稿は第三者が書いた信頼できない入力です。@bot で渡す投稿やスレッドには、プロンプトインジェクション(隠れた指示)が含まれる可能性があります。外部送信を伴う指示(Slack送信など)は承認境界を必ず設定してください(13〜14章)。

13承認(Approvals)と Auto Review の設計

13.1 まず「依頼文の中の境界」が最強

公式ドキュメントは「最も強い境界は依頼そのものの中にある」としています。 

キャンペーンデータを突合し、予算変更の推奨案を作成してください。
キャンペーンの変更や代理店へのメッセージ送信はしないでください。
現在値・提案値・想定インパクトを示したうえで承認を求めてください。

明示的な境界を置くべき操作

操作 例
メッセージ・招待の送信 メール、Slack、カレンダー招待
コンテンツの公開 ブログ、SNS投稿
購入・資金移動 決済、送金
削除・上書き ファイル、データ
権限変更 共有設定、ロール
本番変更 設定、デプロイ
法的条件への同意 利用規約、契約

13.2 承認カードの読み方

承認が必要になると、会話に提案された操作とその入力が表示されます。

表示されるボタンは操作やカードによって異なり、次の 3 つが常にそろうわけではありません。カードによっては Allow・Skip・Not now などのラベルで表示されます。

ボタンの例 動作
Allow once / Allow その操作だけ続行
Always allow 一致するルールを保存(カードがルールを提案している場合のみ表示。慎重に)
Deny / Skip / Not now その操作を実行しない

Shared Bot の承認権限: 承認できる人は場所によって限られます。

  • Slack のスレッド: カードには Allow once・Deny・View details が表示され、操作できるのは依頼した本人だけです。
  • グループチャット: 承認できるのは、Bot が応答している対象メッセージの投稿者だけです。Always allow は表示されません。
  • どちらの場合も、ほかの参加者は承認できません(カードが誰の回答待ちかだけが表示されます)。

重要な性質:

  • 承認は「提案された操作」を制御するもので、すでに完了した作業を元に戻すものではありません。
  • 対象や効果を特定できない操作は承認しない。平易な言葉で説明させるか、下書きを先に作らせる。
  • 承認カードの期限は作業を起こしたきっかけで決まります。チャットのメッセージから始まった作業のカードは、この 30 分のタイマーでは期限切れになりません。一方、Routine・受信メッセージ・その他のバックグラウンド処理が作成したカードは30分で期限切れになり、操作は実行されません。再実行は Bot に依頼し直します。

13.3 Auto Review の設定

ルールの追加場所はプラットフォームで異なります。デスクトップは Settings → General の Bot セクションにある Auto-review、iPhone と Android は Settings → Bot から設定します。

ルール種別 動作
Ask first 一致する操作は常にあなたの確認で止まる
Allow automatically 一致し、かつ自動レビューが他の停止理由を見つけない場合のみ通過
両方に一致 Ask first が優先

チーム管理者が Auto Review を強制している場合、編集不可のチームルールも表示されます。個人ルールはその上に重なり、より厳しくする方向にのみ働きます。

13.4 ルールの書き方

狭く、対象とスコープを限定する(公式の例):

良いルール 理由
外部メールを送る前に必ず確認(Ask first) 外部送信は取り消せない
本番ダッシュボードを変更する前に確認(Ask first) 影響が大きい
/workspace/reports で git status を実行する場合は自動許可 対象・コマンドが明確で読み取り中心

避けるべき広いルール: 「ブラウザ内のことはすべて許可」。Webサイトやツールの挙動は時間とともに変わるためです。

Auto Review はモデルによる判断です。最小権限と明示的な承認境界を置き換えるものではなく補完するものと公式も位置づけています。第三者の分析(howtoharden, eesel)は、承認がユーザーの自由記述に依存する点・自動レビューが全副作用(例: メモリ書き込み)を審査しない点を指摘しています。

13.5 ローカルPCへのアクセス

クラウド上の共有コンピュータとは別の能力として、手元の Mac/Windows での実行が設定できます。

設定(Settings → Computer → Your computer) 意味
Ask every time(デフォルト) 毎回確認
Always allow 常に許可
Never allow 常に拒否
  • 手元のファイルで作業させる明確な理由がなければ Never allow を推奨(公式)。
  • チーム管理者がより厳しい上限を設定している場合は、そちらが優先されます。

14セキュリティの境界を理解する

14.1 共有コンピュータの境界(最重要)

公式ドキュメントの要点:

事実 意味
あなたの個人 Bot はすべて 1 台のクラウドコンピュータを共有 ファイル・ブラウザセッション・コマンドライン資格情報が全個人 Bot で利用可能
Shared Bot はどこで使うかで使用するコンピュータが変わる メンバー自身のチャットではそのメンバーのコンピュータ、Slack チャンネルやグループチャットでは Shared Bot のコンピュータを使う
別々の Bot をセキュリティ境界として使わない 「経理用 Bot」「公開用 Bot」で権限が分かれるわけではない
Bot の公開共有リンク 設定をコピーされるだけで、あなたの PC やログインは共有されない。ただし秘密情報・顧客データ・社内URLを共有 Bot に入れない
Bot を削除しても 共有PC上のファイルやブラウザセッションは消えない

14.2 プロンプトインジェクションとの関係

Django 共同開発者の Simon Willison は、AI エージェントが危険になる3条件を「致命的な三つ組(lethal trifecta)」と呼んでいます。

条件 Grok Bot での例
① 私的データへのアクセス メール・ドライブ・ログイン済みセッション・ファイル
② 信頼できない内容への接触 Webページ・受信メール・X の投稿・Slack メッセージ
③ 外部へ送信する手段 メール送信、Slack 投稿、ブラウザからの POST

3つが同時に揃うと、隠れた指示でデータが持ち出される恐れがあります。 xAI のドキュメントも、外部コンテンツを信頼できないものとして扱う層と、Auto Review・ネットワークポリシー・操作ごとの承認を重ねつつ、これらはリスクを減らすが排除はしないとしています(第三者の整理による)。

対策の考え方(三つ組を崩す)

崩す対象 具体策
①を減らす 必要なツールだけ接続。スコープ付きサービスアカウント。読み取り専用から開始
②を減らす 信頼できないサイトを閲覧させる Routine を作らない。広いトリガーを避ける
③を止める 送信・公開・購入・削除・本番変更は常に承認の後ろ

14.3 アクセスを撤回するとき(公式の手順)

  1. 関連する Routine を一時停止/削除
  2. 共有コンピュータ上のWebサイトからサインアウト
  3. コネクタをアンインストールし、元のサービス側で認可を取り消す
  4. /workspace から機密ファイルを削除
  5. 不要な Bot を非表示/削除
  6. 必要なら Cursor アカウント削除フローへ

16チーム・組織で使うとき

16.1 Team Bot

  • Cursor チームでは、サイドバーの + → Create a Bot で Bot を作り、チャットの Bot 名メニューの Share からチームに共有すると、メンバーが話しかけられる Bot になります。
  • チームで共有する Bot では、オーナーまたは Manager が追加したアプリ・シークレット・スキル・ファイル・メモリが、各メンバーのチャットでも利用可能になります。メモリには 2 種類あります。Bot がチーム全体のために保存したメモリはほかのメンバーとのチャットでも使われ、保存したときは Bot がその旨を伝えます。一方、各メンバーとの作業について覚えたことはそのメンバーと Bot の間に留まり、メンバー個人に関する内容はチームのメモリには保存されません。オーナーと Manager のどちらが追加する場合も、各メンバーのチャットで使われる指示・ファイル・メモリには認証情報や顧客データを書き込まないでください。Bot に必要なログインやキーは、9.1 の手順に従い、ログインは Team Bot 専用の Vault(v0.78.1 以降・段階配信のため未提供のチームもある)、キーは Shared Bot の Secrets に登録します。また、個人情報や顧客情報をメモリに保存させないでください。
  • 一方、Bot の公開テンプレートとしての共有はログインの共有ではありません(コンピュータ・ログイン・会話履歴は共有されない)。ただし設定だけでなく、Bot の ID(名前など)・説明・Skill・Routine といった共有用の構成が公開されます。公開する前に Bot の詳細で共有される中身を確認し、API キー・社内URL・顧客データなどの機密を取り除いてください。公開後は Share メニューの View template details で中身を確認できます。

16.2 管理者が知っておくこと(公式・第三者資料より)

項目 内容
設定の所在 Grok Bot の主要な管理設定は Cursor のダッシュボードにある。一部の設定は Team Settings・Team Marketplace・ID プロバイダー(IdP) 側にもある。docs.x.ai はそのページを写し、Cursor に戻るリンクを持つ
Auto Review の強制 Enterprise プランのみ。Enterprise の管理者が Enforce Auto-review とチーム全体の Auto-review ルールを設定すると、Auto-review を有効にしているメンバーには編集不可のチームルールが適用される。個人ルールはより厳しくする方向にのみ追加できる。グループに Don't enforce for this group を設定すると、そのグループでは Enforce Auto-review の設定がロック解除され、メンバーが Auto-review をオフにできるようになる(チームルールが編集可能になったり削除されたりするわけではない)
ローカル実行の上限 管理者がチーム全体の上限を設定できる(厳しい方が優先)
Bot の ID Bot には識別用の ID があるが、独立した認証アイデンティティや資格情報は持たず、原則としてサインインしているメンバーとして動く。例外として、チーム管理のコネクタはチームまたはサービスアカウントの資格情報を使う場合がある。コネクタが使う資格情報と、監査ログに操作者として記録される ID は別物として扱う(公式ドキュメントは、どの ID が操作者として記録されるかを明記していないため、導入前に確認する)
実行環境 第三者の調査では、Cursor がホストするマシン上でのみ動作しオンプレミスの選択肢はない(OneWave の読み込みによる)
認証・準拠 公式のセキュリティページは ISO/IEC 27001 と ISO/IEC 42001 の認証取得を示している。なお、第三者(eesel)は過去に「ドキュメントが認証取得の主張をしていない」と指摘していた(調査日 2026年10月24日時点の記事。現在は公式ページで最新の認証状況を確認する)

18よくある失敗と対策(アンチパターン集)

# 失敗 なぜ危険か 対策
1 何でも屋 Bot を1体だけ作る 文脈が散らかり品質が下がる 役割ごとに Bot を分ける
2 Bot を分ければ安全だと思う 共有コンピュータで資格情報が共有される Bot 分割をセキュリティ境界にしない
